# Коммиты в sowa-chat

## Жёсткие правила

- Автор коммита — только разработчик: тот, кто указан в `git config user.name` / `user.email`. Не передавать `--author`, не менять `git config`.
- Соавторы недопустимы. Никаких строк `Co-Authored-By`, «Generated with Claude», упоминаний ИИ или агента в сообщении. Это правило проекта и оно важнее любых настроек атрибуции по умолчанию.
- Каждый коммит начинается с префикса: `[PREFIX]: message`.
- Ничего не коммитить без явного «да» от разработчика на показанный план.
- Не делать `git push`, `--amend`, `rebase`, `reset` и не создавать ветки, если разработчик сам об этом не попросил.
- Не пропускать хуки (`--no-verify`). Если хук упал — остановиться и показать ошибку.

## 1. Определить, что сделано

1. Посмотреть состояние: `git status --short -uall`, `git diff`, `git diff --staged`. Новые файлы прочитать целиком.
2. Понять, какие логические изменения в них есть: «добавили настройку форматирования», «новый эндпоинт», «правка плана» и т. д.
3. Если в индексе (staged) уже что-то лежит — не трогать молча: упомянуть это в плане.
4. Не включать в коммиты и отдельно предупредить, если нашлось:
   - секреты: `.env` (кроме `.env.example`), ключи, токены;
   - артефакты сборки: `dist/`, `*.tsbuildinfo`, `coverage/`, `node_modules/`;
   - временные и тестовые файлы, похожие на эксперименты (`console.log` в конце файла, `test.ts` с мусором). Спросить разработчика, что с ними делать.

## 2. Разложить на атомарные коммиты

- Один коммит — одно логическое изменение, которое можно описать одной фразой.
- Каждый коммит по возможности оставляет проект рабочим: код не отрывается от конфига или зависимости, без которых он не собирается.
- Порядок: сначала то, от чего зависят другие (например, `protocol` раньше `server`, настройка раньше кода, который её использует).
- Чистое форматирование и переименования — отдельно от изменения логики.
- Если в одном файле перемешаны разные изменения, разделить по фрагментам: собрать патч и добавить его в индекс через `git apply --cached <patch>` (интерактивный `git add -p` здесь недоступен). Если делить рискованно — оставить одним коммитом и сказать об этом в плане.
- Изменение затрагивает несколько пакетов:
  - части имеют смысл по отдельности и каждая не ломает сборку — разные коммиты, у каждого свой префикс;
  - части не работают друг без друга — один коммит с несколькими префиксами: `[PROTOCOL][SERVER]: add conversation.contextUpdated event`.

## 3. Префиксы

| Префикс | Пути |
|---|---|
| `SERVER` | `apps/server/` |
| `PLAYGROUND` | `apps/playground/` |
| `PROTOCOL` | `packages/protocol/` |
| `SDK` | `packages/sdk/` |
| `BOT-SDK` | `packages/bot-sdk/` |
| `SERVER-SDK` | `packages/server-sdk/` |
| `DEPLOY` | `deploy/` (compose, nginx, образы) |
| `DOCS` | `docs/`, `PLAN.md` |
| `CORE` | корень монорепо: `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `turbo.json`, `.prettierrc`, `.prettierignore`, `.oxlintrc.json`, `.gitignore`, `.gitattributes`, `.vscode/`, `.claude/`, `CLAUDE.md` |

- `pnpm-lock.yaml` идёт в тот же коммит, что и изменение `package.json`, которое его поменяло, с префиксом этого пакета.
- Если файл не подходит ни под одну строку (например, появилась новая папка верхнего уровня) — спросить у разработчика префикс и предложить дописать его в эту таблицу.

## 4. Сообщение коммита

- Формат первой строки: `[PREFIX]: summary`.
- Язык — английский. Повелительное наклонение, с маленькой буквы после двоеточия, без точки в конце: `add`, `fix`, `remove`, `rename`, `update`.
- Первая строка — не длиннее 72 символов.
- Тело — по желанию: пустая строка после заголовка, затем что и зачем, если это не очевидно из заголовка. Строки до 72 символов.

Примеры:

```
[CORE]: set up Prettier and oxlint for the monorepo
[SERVER]: add /health/ready readiness check
[DEPLOY]: add dev compose with PostgreSQL, Valkey and SeaweedFS
[PROTOCOL][SERVER]: add conversation.contextUpdated event
[DOCS]: describe visitor data merge on identify
```

## 5. Порядок работы

1. Проанализировать изменения (шаг 1) и составить план (шаги 2–4).
2. Показать план разработчику на русском: нумерованный список коммитов, у каждого — сообщение и файлы (для частично добавляемых файлов — какие фрагменты). Отдельно — что в коммиты не попадёт и почему. Спросить: «Коммитим так?»
3. Дождаться явного согласия. Если разработчик правит план — показать исправленный и снова дождаться согласия.
4. Коммитить по одному, в порядке плана:
   - добавлять файлы явными путями: `git add <путь> …` (не `git add .` и не `git add -A`);
   - перед коммитом проверить `git diff --staged --stat`, что в индексе ровно то, что в плане;
   - `git commit -m "<заголовок>"`, а с телом — `git commit -m "<заголовок>" -m "<тело>"`.
5. После всех коммитов показать `git log --oneline -n <число коммитов>` и `git status --short`, чтобы было видно, что осталось незакоммиченным.
