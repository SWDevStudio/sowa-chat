# Эпик в sowa-chat

Основная сессия — менеджер. Она создаёт ветку, запускает субагентов, выполняет проверки, меняет статусы и останавливается там, где решает разработчик. Код и тесты менеджер не пишет, файлы задач не правит, кроме статусов.

Команда `/epic N` — уже ответ на уточняющие вопросы из CLAUDE.md. До точки остановки ничего не спрашивать.

## Жёсткие правила

- Вся работа — в ветке `feature/EPIC-N`. Отдельных веток для задач нет.
- Задачи выполняются по одной, в основной папке проекта. Без worktree и без параллельных исполнителей.
- `master` не трогать: не сливать в него, не пушить. Никаких `push`, `rebase`, `reset`, `--force`, `--amend`, `--no-verify`.
- PLAN.md не читать: всё нужное записано в файлах задач.
- В процессе эпика коммиты делают `epic-tester`, `epic-worker` и менеджер без согласования с разработчиком — это исключение из скилла git-commit. Формат сообщений тот же: префиксы и правила из `.claude/skills/git-commit/SKILL.md`, разделы 3 и 4. Без `Co-Authored-By` и упоминаний ИИ.
- Файлы в коммит добавлять явными путями (`git add <путь>`), не `git add .`.

## Точки остановки

Менеджер останавливается, пишет разработчику, что случилось и что нужно от него, и ждёт ответа:

1. Приёмочные тесты написаны — на утверждение.
2. Очередная задача с исполнителем «разработчик».
3. Субагент вернул вопрос.
4. Тестировщик решил, что неверен сам тест.
5. Задача не прошла проверку после доработки Sonnet.
6. Эпик готов — итоговый отчёт с ревью.
7. При старте есть незакоммиченные правки, или git выдал ошибку, которую не решить без отмены чужих изменений.

## 1. Старт или продолжение

1. Прочитать `tasks/EPIC-N/README.md`: таблица задач и строка «Нужны эпики». В `tasks/README.md` найти статусы этих эпиков.
2. Какой-то эпик из «Нужны эпики» не «готов» — сказать об этом и закончить.
3. `git status --short` не пустой — точка остановки 7: спросить, закоммитить правки через git-commit, убрать их в stash или остановиться.
4. Ветки `feature/EPIC-N` нет — `git switch -c feature/EPIC-N master`. Есть — `git switch feature/EPIC-N` и продолжить с того места, где остановились:
   - нет `tasks/EPIC-N/TESTS.md` — с раздела 2;
   - `TESTS.md` есть, а все задачи «не начата» — спросить, утверждены ли тесты;
   - иначе — с раздела 3, с первой задачи, которая не «готова».
5. В `tasks/README.md` поставить эпику статус «в работе».

## 2. Приёмочные тесты

1. Запустить `epic-tester` (инструмент Agent, `subagent_type: epic-tester`) с заданием: «Режим tests, эпик N».
2. Тестировщик коммитит тесты и `tasks/EPIC-N/TESTS.md` и возвращает таблицу «тест → задача → критерий», принятые им имена и то, что проверяется только вручную.
3. Точка остановки 1: показать это разработчику.
4. Разработчик просит правки — снова `epic-tester` в режиме tests, замечания передать дословно. Утвердил — к разделу 3.

## 3. Задачи

Порядок — по номерам. Задача берётся, когда все задачи из её колонки «Зависит от» в статусе «готова». Задачи «готова» пропускаются.

Для каждой задачи:

1. Исполнитель «разработчик» — точка остановки 2. Продолжать, когда разработчик скажет, что задача сделана.
2. Запомнить текущий коммит: `git rev-parse HEAD` — это начало задачи.
3. В `tasks/EPIC-N/README.md` поставить задаче статус «в работе». Не коммитить: статус коммитится в шаге 7.
4. Запустить `epic-worker` (`subagent_type: epic-worker`) с `model` из колонки «Исполнитель» (`haiku` или `sonnet`). Передать: путь к файлу задачи, что ветка `feature/EPIC-N` уже выбрана, путь к `tasks/EPIC-N/TESTS.md`. При доработке — ещё и вердикт тестировщика.
5. Исполнитель вернул вопрос — точка остановки 3.
6. Исполнитель сообщил, что готово, — выполнить проверки задачи (раздел 4).
7. Проверки прошли — статус «готова», коммит `[DOCS]: mark EPIC-N TASK-M done` с файлом `tasks/EPIC-N/README.md`.
8. Проверки упали — разбор падения (раздел 5).

## 4. Проверки задачи

Пакет задачи определить по разделу «Где» в файле задачи: `apps/server` — `@sowa-chat/server`, `packages/protocol` — `@sowa-chat/protocol` и так далее по `name` в `package.json` пакета. Задача может затрагивать несколько пакетов — проверить каждый.

1. Приёмочные тесты не тронуты: `git diff --name-only <начало задачи>..HEAD` не содержит файлов из `TESTS.md`. Содержит — проверка упала.
2. `pnpm lint`.
3. `pnpm --filter <пакет> check-types`, если у пакета есть такой скрипт.
4. Тесты: `pnpm --filter <пакет> exec vitest run <файлы>`, где файлы — unit-тесты из `TESTS.md` этой задачи и всех задач эпика в статусе «готова». E2e-тесты (`*.e2e-spec.ts`) на этом шаге не запускаются.

Приёмочные тесты задач, которые ещё не сделаны, ссылаются на код, которого пока нет. Ошибки линтера и типов в файлах из `TESTS.md` у задач не в статусе «готова» не считаются: проверка прошла, если других ошибок нет.

## 5. Разбор падения

1. Запустить `epic-tester` с заданием: «Режим triage, эпик N, задача M, исполнитель <модель последней попытки>, начало задачи <коммит>», и вывод упавшей команды целиком.
2. Тестировщик дописывает «Историю доработок» в файл задачи, коммитит её и возвращает вердикт: виновата задача (номер), неверен тест или проблема окружения.
3. Неверен тест — точка остановки 4. Тесты меняет только тестировщик и только после согласия разработчика.
4. Проблема окружения (не запущен Docker, занят порт) — сказать разработчику, что исправить, и остановиться.
5. Виновата задача:
   - последняя попытка была у `haiku` — статус «на доработке», запустить `epic-worker` с `model: sonnet` и вердиктом, дальше как в разделе 3 с шага 5;
   - последняя попытка была у `sonnet` — статус «на доработке», точка остановки 5.

Модель последней попытки видна в «Истории доработок» задачи. Если истории нет — это модель из колонки «Исполнитель».

## 6. E2e и полный прогон

Когда все задачи «готова»:

1. E2e: `pnpm --filter @sowa-chat/server test:e2e`. Нужен запущенный Docker.
2. Полный прогон: `pnpm format:check`, `pnpm lint`, `pnpm check-types`, `pnpm test`. Здесь исключений для приёмочных тестов уже нет.
3. Что-то упало — разбор падения (раздел 5). Тестировщик сам определит, какая задача виновата. После исправления снова весь раздел 6.

## 7. Ревью и отчёт

1. `git log --name-only --format= master..feature/EPIC-N` затрагивает `apps/server/`, `packages/bot-sdk/`, `packages/server-sdk/` или `packages/protocol/` — запустить `backend-reviewer` с диапазоном `master..feature/EPIC-N`.
2. В `tasks/README.md` поставить эпику статус «на ревью», коммит `[DOCS]: mark EPIC-N for review`.
3. Точка остановки 6. Отчёт:
   - задачи и кто их сделал, с доработками;
   - `git log --oneline master..feature/EPIC-N`;
   - результаты e2e и полного прогона;
   - что проверяется только вручную (из `TESTS.md`);
   - замечания ревьюера как есть.
4. Какие замечания исправлять, решает разработчик. Выбранные замечания передать `epic-worker` с `model: sonnet`, затем снова раздел 6 и этот раздел.
5. Слияние в `master` и статус «готов» — дело разработчика.
