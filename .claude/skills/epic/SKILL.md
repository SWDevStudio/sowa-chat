# Эпик в sowa-chat

Основная сессия — менеджер. Она создаёт ветку, запускает субагентов, выполняет проверки, меняет статусы, коммитит и останавливается там, где решает разработчик. Код и тесты менеджер не пишет, файлы задач не правит, кроме статусов.

Команда `/epic N` — уже ответ на уточняющие вопросы из CLAUDE.md. До точки остановки ничего не спрашивать.

Каждая задача проходит один цикл: **тесты → реализация → проверки → согласование с разработчиком → коммит**.

## Жёсткие правила

- Вся работа — в ветке `feature/EPIC-N`. Отдельных веток для задач нет.
- Задачи выполняются по одной, в основной папке проекта. Без worktree и без параллельных исполнителей.
- `master` не трогать: не сливать в него, не пушить. Никаких `push`, `rebase`, `reset`, `--force`, `--amend`, `--no-verify`.
- PLAN.md не читать: всё нужное записано в файлах задач.
- Субагенты не коммитят. Коммитит менеджер, и только после согласия разработчика на результат задачи. Это заменяет план коммитов и `git-committer` из скилла git-commit. Формат сообщений тот же: префиксы и правила из `.claude/skills/git-commit/SKILL.md`, разделы 3 и 4. Без `Co-Authored-By` и упоминаний ИИ.
- Файлы в индекс добавлять явными путями (`git add <путь>`), не `git add .`.

## Точки остановки

Менеджер останавливается, пишет разработчику, что случилось и что нужно от него, и ждёт ответа:

1. Задача прошла проверки — на согласование.
2. Очередная задача с исполнителем «разработчик».
3. Субагент вернул вопрос.
4. Тестировщик решил, что неверен сам тест.
5. Задача не прошла проверку после доработки Sonnet.
6. Эпик готов — итоговый отчёт с ревью.
7. При старте есть незакоммиченные правки, или git выдал ошибку, которую не решить без отмены чужих изменений.

## 1. Старт или продолжение

1. Прочитать `tasks/EPIC-N/README.md`: таблица задач и строка «Нужны эпики». В `tasks/README.md` найти статусы этих эпиков.
2. Какой-то эпик из «Нужны эпики» не «готов» — сказать об этом и закончить.
3. Ветки `feature/EPIC-N` нет — `git status --short` должен быть пустым, иначе точка остановки 7. Затем `git switch -c feature/EPIC-N master`.
4. Ветка есть — `git switch feature/EPIC-N` и продолжить:
   - у какой-то задачи статус «в работе» или «на доработке» — задача прервалась на середине. Показать `git status --short` и спросить: продолжить её с проверок (раздел 3, шаг 6) или разработчик сам откатит её незакоммиченные правки и задача начнётся заново;
   - такой задачи нет, а `git status --short` не пустой — точка остановки 7;
   - иначе — с первой задачи, которая не «готова».
5. В `tasks/README.md` поставить эпику статус «в работе».

## 2. Порядок задач

По номерам. Задача берётся, когда все задачи из её колонки «Зависит от» в статусе «готова». Задачи «готова» пропускаются. Все задачи «готова» — раздел 5.

## 3. Цикл задачи

1. Исполнитель «разработчик» — точка остановки 2. Продолжать, когда разработчик скажет, что задача сделана.
2. В `tasks/EPIC-N/README.md` поставить задаче статус «в работе».
3. **Тесты.** Запустить `epic-tester` (инструмент Agent, `subagent_type: epic-tester`) с заданием: «Режим tests, эпик N, задача M». Он пишет тесты только этой задачи и возвращает список файлов тестов, принятые имена и ручные проверки. Тесты других задач эпика пишутся в их собственных циклах. Вопрос — точка остановки 3.
4. Добавить файлы тестов в индекс: `git add <файлы тестов>`. Так менеджер увидит, если исполнитель их изменит.
5. **Реализация.** Запустить `epic-worker` (`subagent_type: epic-worker`) с `model` из колонки «Исполнитель» (`haiku` или `sonnet`). Передать: путь к файлу задачи, что ветка `feature/EPIC-N` уже выбрана, список файлов тестов. При доработке — ещё вердикт тестировщика или замечания разработчика дословно. Вопрос — точка остановки 3.
6. **Проверки** (раздел 4). Упали — разбор падения (раздел 6), потом снова этот шаг.
7. **Согласование** — точка остановки 1. Показать:
   - что сделано, из ответа исполнителя;
   - `git status --short` и `git diff --stat HEAD`;
   - файлы тестов и какие критерии приёмки они проверяют;
   - результаты проверок;
   - что проверяется только вручную;
   - принятые тестировщиком имена.
8. Разработчик просит правки:
   - к коду — `epic-worker` с моделью последней попытки и замечаниями дословно;
   - к тестам — `epic-tester` в режиме tests с замечаниями дословно, затем снова `git add <файлы тестов>`.
   
   Потом снова шаг 6.
9. **Коммит.** Разработчик согласен:
   - статус задачи «готова»;
   - коммит кода и тестов: все изменённые и новые файлы вне `tasks/` из `git status --short`. Сообщение — суть задачи на английском, префиксы по затронутым пакетам;
   - коммит `[DOCS]: mark EPIC-N TASK-M done` с файлами из `tasks/`: статус и «История доработок».

## 4. Проверки задачи

Пакет задачи определить по разделу «Где» в файле задачи: `apps/server` — `@sowa-chat/server`, `packages/protocol` — `@sowa-chat/protocol` и так далее по `name` в `package.json` пакета. Задача может затрагивать несколько пакетов — проверить каждый.

1. Тесты не тронуты: `git diff --name-only -- <файлы тестов>` пустой. Не пустой — проверка упала.
2. `pnpm lint`.
3. `pnpm --filter <пакет> check-types`, если у пакета есть такой скрипт.
4. `pnpm --filter <пакет> test`, если у пакета есть такой скрипт. Так заодно проверяются тесты уже сделанных задач. E2e-тесты (`*.e2e-spec.ts`) на этом шаге не запускаются.

Всё должно пройти без ошибок.

## 5. E2e, полный прогон, ревью и отчёт

Когда все задачи «готова»:

1. E2e: `pnpm --filter @sowa-chat/server test:e2e`. Нужен запущенный Docker.
2. Полный прогон: `pnpm format:check`, `pnpm lint`, `pnpm check-types`, `pnpm test`.
3. Что-то упало — разбор падения (раздел 6): тестировщик сам определит, какая задача виновата. Задаче статус «на доработке», дальше цикл задачи с шага 5. После её коммита снова этот раздел.
4. `git log --name-only --format= master..feature/EPIC-N` затрагивает `apps/server/`, `packages/bot-sdk/`, `packages/server-sdk/` или `packages/protocol/` — запустить `backend-reviewer` с диапазоном `master..feature/EPIC-N`.
5. В `tasks/README.md` поставить эпику статус «на ревью», коммит `[DOCS]: mark EPIC-N for review`.
6. Точка остановки 6. Отчёт:
   - задачи и кто их сделал, с доработками;
   - `git log --oneline master..feature/EPIC-N`;
   - результаты e2e и полного прогона;
   - замечания ревьюера как есть.
7. Какие замечания исправлять, решает разработчик. Выбранные замечания передать `epic-worker` с `model: sonnet`, затем проверки, согласование, коммит и снова этот раздел.
8. Слияние в `master` и статус «готов» — дело разработчика.

## 6. Разбор падения

1. Запустить `epic-tester` с заданием: «Режим triage, эпик N, задача M, исполнитель <модель последней попытки>», и вывод упавшей команды целиком.
2. Тестировщик дописывает «Историю доработок» в файл задачи и возвращает вердикт: виновата задача (номер), неверен тест или проблема окружения.
3. Неверен тест — точка остановки 4. Тесты меняет только тестировщик и только после согласия разработчика.
4. Проблема окружения (не запущен Docker, занят порт) — сказать разработчику, что исправить, и остановиться.
5. Виновата задача:
   - последняя попытка была у `haiku` — статус «на доработке», `epic-worker` с `model: sonnet` и вердиктом (раздел 3, шаг 5);
   - последняя попытка была у `sonnet` — статус «на доработке», точка остановки 5.

Модель последней попытки видна в «Истории доработок» задачи. Если истории нет — это модель из колонки «Исполнитель».
