# Push в sowa-chat

## Жёсткие правила

- Никаких `--force`, `--force-with-lease`, `--no-verify`, `rebase`, `reset`, `--amend` и удаления веток, если разработчик сам об этом не попросил.
- Не трогать незакоммиченные правки разработчика без его решения.
- Исправления после ошибок хука не коммитить и не пушить повторно: показать и остановиться. Закоммитить их — через скилл git-commit, когда разработчик попросит.

## 1. Подготовка

1. Посмотреть состояние: `git status --short`, `git branch -vv`, `git remote -v`.
2. Нет remote или у ветки нет upstream — сообщить об этом и спросить адрес remote и ветку. Remote добавлять (`git remote add`) только после ответа. Первый push — `git push -u <remote> <ветка>`.
3. Upstream есть, но новых коммитов нет (`git log --oneline @{u}..HEAD` пуст) — сказать, что пушить нечего, и закончить.
4. Есть незакоммиченные правки — предупредить: pre-push проверяет рабочую копию, и они могут уронить проверки.

## 2. Ревью перед push

1. Определить коммиты, которые уйдут: `git log --oneline @{u}..HEAD`, а при первом push — все коммиты ветки, которых нет на remote.
2. Запустить субагента `reviewer` (инструмент Agent, `subagent_type: reviewer`) и передать ему этот диапазон коммитов.
3. Замечаний нет — переходить к push. Есть — показать их разработчику и спросить: пушить как есть, сначала исправить или отменить.

## 3. Push и ошибки Husky

1. Выполнить `git push` (или `git push -u <remote> <ветка>` при первом push).
2. Хук pre-push выполняет по порядку `pnpm format:check` → `pnpm lint` → `pnpm check-types` → `pnpm test` и останавливается на первом упавшем шаге. По выводу определить шаг и файлы.
3. Ошибка в незакоммиченных правках (файл есть в `git status`) — не исправлять. Показать и спросить, что делать:
   - закоммитить их (через git-commit);
   - убрать в stash на время push: `git stash push -- <файлы>`, push, `git stash pop`;
   - остановиться.
4. Ошибка в закоммиченном коде:
   - простая, исправляется без решений по логике — формат (`pnpm format`), автоисправимый линтер (`pnpm exec oxlint --fix <файл>`), очевидная опечатка в импорте или типе: исправить, показать diff и остановиться;
   - сложная — падают тесты, неочевидные ошибки типов, нужно решение по логике: не исправлять наугад, показать шаг, ошибку и варианты, спросить разработчика.
5. Ошибка не от хука — сеть, нет прав, remote отклонил push, ветка разошлась с remote (non-fast-forward): показать и спросить. Никакого force.

## 4. Итог

Показать, что ушло (`git log --oneline` по диапазону), результат ревью и `git status --short`.
