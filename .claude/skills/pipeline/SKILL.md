# Конвейер эпиков

Основная сессия — менеджер конвейера, она работает на sonnet. Она по очереди планирует эпики, ведёт их по скиллу `epic` и вливает в ветку `pipeline`. Сама ничего сложного не решает: выбор эпика делает скрипт, планирование — `epic-planner`.

Команда `/pipeline` — разрешение работать до итогового отчёта. До него разработчику ничего не писать и ничего не спрашивать. Исключение — проверки при старте (раздел 1).

## Жёсткие правила

- Основная сессия — на sonnet. Если она на другой модели — сказать разработчику «переключитесь: `/model sonnet`» и закончить.
- Интеграционная ветка — `pipeline` от `master`. Каждый эпик идёт в `feature/EPIC-N` от `pipeline` и после итогового прогона вливается в `pipeline`. `master` не трогать.
- Эпики, которым не нужны друг другу (строка «Нужны эпики» в README), разработчик разрешил вести одновременно, чтобы конвейер не простаивал. Каждый такой эпик идёт в своей копии репозитория (`git worktree add ../hector-chat-epic-N feature/EPIC-N`) со своим `pnpm install`. После слияния эпика копия удаляется сразу: `git worktree remove --force ../hector-chat-epic-N`. Технические ветки и worktree (задач, проверок, копий) не копятся: после использования удаляются сразу. Эпик, которому нужен ещё не влитый эпик, ждёт его слияния в `pipeline`. Влитие в `pipeline` идёт по одному. Скрипты `.claude/scripts/epic/` запускаются из каталога копии: корень определяется по текущему чекауту. Агентам передавать путь копии и путь worktree задачи. Лимиты агентов и прогонов общие на все эпики.
- Файлы `tasks/EPIC-N/TASK-M.md` в репозитории — черновики. Перед эпиком, когда код всех нужных эпиков уже в `pipeline`, `epic-planner` в режиме check (на sonnet) сверяет их с решениями влитых эпиков и текущим кодом. Если расхождений нет, он только дописывает колонки таблицы и строку «Ревью». Если есть, `epic-planner` в режиме plan (на opus) правит то, что с ними связано: может менять число задач, порядок, исполнителей и расписывать новые задачи. Планировщику можно задавать вопросы (режим question). Остальные субагенты работают только в рамках своей задачи и PLAN.md не читают.
- Внутри эпика действуют все правила скилла `epic`, кроме его точек остановки.
- После ответа `epic-planner` и `pipeline-analyst` менеджер записывает их в журнал так же, как в скилле `epic` (раздел «Жёсткие правила»): `log-agent.mjs N - epic-planner-check sonnet …`, `log-agent.mjs N - epic-planner-plan opus …`, `log-agent.mjs 0 - pipeline-analyst sonnet …`.
- Лимиты — раздел «Субагенты и прогоны» в CLAUDE.md.
- Никаких `push`, `--force`, `--amend`, `--no-verify`, `rebase` и `reset` веток `pipeline` и `feature/EPIC-N`.
- Состояние конвейера — `.claude/pipeline-state.md` (в `.gitignore`): ведётся так, чтобы после `/clear` или обрыва можно было продолжить: по каждому эпику в работе — номер, этап (планирование, эпик, слияние), путь копии репозитория, какие задачи в каком состоянии, какие агенты идут; плюс временный лимит разработчика. Скилл `epic` начинает с `.claude/epic-state.md`: для эпика в отдельной копии он лежит в этой копии. Пропущенные эпики хранит скрипт в `.claude/epic-runs/pipeline-skipped.json`. После обрыва сессии, `/clear` или сжатия контекста начинать с состояния.

## Скрипты

| Скрипт | Что делает | Результат |
|---|---|---|
| `node .claude/scripts/epic/next-epic.mjs` | следующий эпик, у которого все нужные эпики уже в `pipeline`; эпики с невыполненными зависимостями сам помечает пропущенными | `next N` и строки `skipped …` или `done` |
| `node .claude/scripts/epic/skip-epic.mjs N "<причина>"` | пометить эпик пропущенным | строка с причиной |
| `node .claude/scripts/epic/analysis-due.mjs` | сколько задач влито с прошлого анализа | `due K` при 10 и больше, иначе `wait M/10` |
| `node .claude/scripts/epic/analysis-done.mjs K` | записать в журнал, что анализ K сделан | строка `analysis K logged` |
| `node .claude/scripts/epic/log-agent.mjs N <M или -> <роль> <модель> tokens=… durationMs=…` | записать в журнал `.claude/epic-runs/metrics.jsonl`, что агент закончил | строка `logged …` |

## 1. Старт или продолжение

1. Проверить модель основной сессии.
2. Прочитать `.claude/pipeline-state.md`, если он есть.
3. `git status --short` не пустой — показать его и спросить разработчика, что делать. Это единственный вопрос до отчёта.
4. Ветки `pipeline` нет — `git switch -c pipeline master`. Есть — `git switch pipeline`.
5. Эпики «на ревью» из `tasks/README.md`, чьи ветки ещё не влиты в `pipeline`, влить по порядку номеров: `git merge --no-ff --no-edit feature/EPIC-N`. Конфликт — `git merge --abort` и `skip-epic.mjs N "конфликт при слиянии в pipeline"`.
6. Состояние говорит, что эпик прервался посередине, — продолжить его с прерванного этапа раздела 2.

## 2. Цикл эпика

1. **Анализ.** `analysis-due.mjs`. `due K` — `pipeline-analyst` с `model: sonnet` и заданием «Анализ K», затем `analysis-done.mjs K`, `git add -- tasks/pipeline-analysis-K.md` и коммит `[DOCS]: add pipeline analysis K`. Анализ идёт между эпиками на ветке `pipeline`, пока других агентов нет. `wait` — сразу дальше. Предложения аналитика сами в правила и файлы задач не вносятся: они идут в итоговый отчёт.
   Затем `next-epic.mjs`. `done` — раздел 3. `next N` — дальше.
2. **Ветка.** Ветки `feature/EPIC-N` нет — `git switch -c feature/EPIC-N pipeline`. Есть — `git switch feature/EPIC-N`.
3. **Планирование.** В таблице задач README эпика нет колонки «Тесты» — сначала `epic-planner` с `model: sonnet` и заданием «Режим check, эпик N».
   - «Годится» — `git add -- tasks/EPIC-N` и коммит `[DOCS]: add task columns for <тема эпика по-английски>`.
   - «Нужен plan» — `epic-planner` с `model: opus` и заданием «Режим plan, эпик N, расхождения: <список дословно>». Затем `git add -- tasks/EPIC-N` и коммит `[DOCS]: add task files for <тема эпика по-английски>`.
   - «Описать нельзя» (от любого режима) — `skip-epic.mjs N "<причина>"`, `git switch pipeline`, шаг 1.
4. **Эпик.** Вызвать скилл `epic` с аргументами «N, база pipeline» и вести эпик по нему до итогового отчёта в `tasks/EPIC-N/report.md`.
5. **Слияние.**
   - Итоговый прогон эпика прошёл — `git switch pipeline`, `git merge --no-ff --no-edit feature/EPIC-N`.
   - Не прошёл — `git switch pipeline`, `skip-epic.mjs N "итоговый прогон не прошёл"`. Эпики, которые от него зависят, `next-epic` пропустит сам.
6. Шаг 1.

Задачи «на разработчике» внутри влитого эпика конвейер не останавливают. Если следующему эпику без них не обойтись, это увидит `epic-planner` и ответит «описать нельзя».

## 3. Итоговый отчёт

Единственная точка остановки. Отчёт собирается из `tasks/EPIC-N/report.md` влитых эпиков и `.claude/epic-runs/pipeline-skipped.json`. Записать его в `tasks/pipeline-report.md` и коротко повторить разработчику:

- влитые эпики, по каждому — ссылка на его отчёт;
- пропущенные эпики и причина;
- задачи «на разработчике» по всем эпикам;
- ссылки на `decisions.md` эпиков: там публичные имена и решения планировщика;
- ссылки на `tasks/pipeline-analysis-K.md` и пять главных предложений последнего анализа;
- замечания ревью, которые остались;
- ручные проверки;
- `git log --oneline --first-parent master..pipeline`.

Коммит отчёта в `pipeline`: `[DOCS]: add pipeline report`. Слияние `pipeline` в `master` и статус «готов» эпикам — дело разработчика.
