# EPIC-3 / TASK-2. Сквозной requestId

Исполнитель: sonnet
Зависит от: TASK-1
Ветка: feature/EPIC-3

## Что сделать

У каждого HTTP-запроса есть `requestId`, и он попадает во все строки лога этого запроса.

1. Если пришёл заголовок `X-Request-Id` с допустимым значением — использовать его, иначе создать новый UUID. Допустимое значение: до 128 символов, только латиница, цифры, `-`, `_`, `.`. Недопустимое значение заменяется новым ID, чтобы через заголовок нельзя было подделать строки лога.
2. `requestId` хранится в контексте запроса через `nestjs-cls` (AsyncLocalStorage): любой код может получить его без передачи через параметры.
3. Все строки лога, написанные во время запроса, в том числе из сервисов, содержат `requestId`.
4. Ответ содержит заголовок `X-Request-Id` с тем же значением.

## Где

- `apps/server/src/infra/logging/`.
- `apps/server/src/infra/` — подключение `nestjs-cls` (`ClsModule`), если его ещё нет. Транзакции через тот же `nestjs-cls` настроит эпик базы данных: модуль подключается один раз и расширяется.

## Требования из плана

- `requestId` сквозной: api создаёт его на каждый запрос (или берёт из `X-Request-Id`), позже он сохраняется в outbox и в задачах очереди, worker пишет логи с тем же ID, а в вебхуки ботам и подписчикам он уходит заголовком `X-Request-Id`. Весь путь сообщения находится одной командой: `docker compose logs api worker | grep <requestId>`.
- Сейчас нужно только начало цепочки: HTTP-запрос → контекст → логи.

## Критерии приёмки

- Запрос с `X-Request-Id: abc-123`: во всех строках лога этого запроса `requestId` равен `abc-123`, ответ содержит тот же заголовок.
- Запрос без заголовка получает новый UUID.
- Заголовок со значением длиннее 128 символов или со спецсимволами заменяется новым ID.
- Два параллельных запроса не смешивают свои `requestId`.

## Чего не делать

- Не передавать `requestId` в outbox и очереди — это эпик outbox.
