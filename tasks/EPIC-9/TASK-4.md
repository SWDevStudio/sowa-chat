Ветка: feature/EPIC-9

## Что сделать

Сервис шифрования секретов, которые нам нужны в открытом виде (подпись вебхуков ботам и подписчикам).

1. Ключи шифрования — переменная `SOWA_ENCRYPTION_KEYS`: список `версия:ключ` через запятую, ключ — 32 байта в base64. Пример: `1:Base64...,2:Base64...`. Шифрует ключ с наибольшей версией, расшифровывает ключ той версии, что записана в шифротексте.
2. Зашифрованное значение — одна строка, в которой есть версия ключа, IV (12 случайных байт на каждое шифрование), шифротекст и тег аутентификации.
3. Подменённый шифротекст, IV или тег не расшифровывается: ошибка, а не мусор.
4. Объекты ключей создаются один раз при старте.
5. Добавить переменную в модуль конфигурации с проверкой формата.

## Где

- `apps/server/src/infra/crypto/`.
- `apps/server/src/infra/config/`, `apps/server/.env.example`.

## Требования из плана

- Секреты, которые нужны нам в открытом виде, шифруются AES-256-GCM ключом из env, отдельно от БД.
- Ключ шифрования: в каждой зашифрованной записи хранится версия ключа, при ротации записи перешифровывает команда CLI `secrets:reencrypt`.
- В production секреты обязательны в env: без них сервис не стартует. В development их генерирует эпик режимов.

## Критерии приёмки

- Зашифрованная строка расшифровывается обратно.
- Два шифрования одного значения дают разные строки.
- Подменённый байт шифротекста или тега даёт ошибку.
- Значение, зашифрованное ключом версии 1, расшифровывается после добавления ключа версии 2, а новые значения шифруются версией 2.
- Ключ не 32 байта — сервис не стартует.

## Чего не делать

- Не делать перешифровку записей — это команда `secrets:reencrypt` в эпике CLI.
