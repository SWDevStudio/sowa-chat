# sowa-chat: эпики и задачи

Индекс эпиков. У каждого эпика своя папка: `README.md` с целью и таблицей задач, файлы `TASK-M.md` с подробными задачами. Сделанное раньше (монорепо, инструменты, инфраструктура, библиотеки, changesets и dependency-cruiser) сюда не входит.

## Как идёт работа

- Эпик запускается и продолжается командой `/epic N` (скилл `.claude/skills/epic/SKILL.md`). Дальше менеджер ведёт эпик сам до итогового отчёта и по ходу разработчика не спрашивает. Свои решения он записывает в `tasks/EPIC-N/decisions.md`.
- Все оставшиеся эпики подряд ведёт конвейер `/pipeline` (скилл `.claude/skills/pipeline/SKILL.md`). Перед каждым эпиком `epic-planner` пишет его файлы задач по PLAN.md и уже готовому коду, исходя из предложения по разбивке в `tasks/planning/`. Эпики вливаются в ветку `pipeline`, в `master` её сливает разработчик.
- Эпики выполняются по порядку номеров. Эпик — цельный кусок: модуль или функция, которую можно отревьюить одним PR.
- Эпик делается в ветке `feature/EPIC-N` от `master`. Каждая задача идёт в своей технической ветке и worktree, принятая задача вливается в ветку эпика squash-коммитом. Задачи без общих мест в разделе «Где» идут параллельно.
- Цикл задачи: тестировщик пишет тесты задачи → исполнитель делает задачу → тесты задачи, линтер изменённых файлов и типы пакета → приёмка свежим тестировщиком → squash-коммит.
- Во время эпика гоняются только тесты и проверки задачи. E2e и полный прогон — один раз, когда готовы все задачи эпика, до слияния в `master`.
- Упавшую проверку разбирает тестировщик. Задача, которая не прошла, переходит к модели выше: haiku → sonnet → opus. Если не справился opus, задача получает статус «на разработчике».
- Готовый эпик проверяет `backend-reviewer`, существенные замечания исправляются сразу. Потом эпик смотрит разработчик, в `master` сливает он же.
- Лимиты агентов и прогонов — раздел «Субагенты и прогоны» в `CLAUDE.md`.
- Основная сессия идёт на sonnet и только оркестрирует. Механику делают скрипты `.claude/scripts/epic/`, ответы на вопросы субагентов — `epic-planner`.
- Строка «Владеет:» в файле задачи — файлы и папки, которые задача меняет. Задачи с пересечением не идут параллельно.
- Базы данных не создаются автоматически: схема только миграциями, данные — фикстурами.

Колонки таблицы задач эпика:

- «Исполнитель»: **haiku**, **sonnet** или **разработчик** — задача, где решение принимает человек. Задачи, которые от неё зависят, ждут её закрытия.
- «Тесты»: модель тестировщика и приёмки, **opus** или **sonnet**. Opus ставится задачам с безопасностью, конкурентностью и публичным контрактом SDK и протокола. Если колонки нет — opus.
- «Сложность»: **простая** или **обычная**. Простая — одна-две правки по готовому образцу, без безопасности, конкурентности, публичного контракта SDK и протокола: приёмку свежим тестировщиком для неё пропускают, проверки `check-task` идут как у всех. Остальное — обычная. Если колонки нет — обычная.

Строка «Ревью» в README эпика — модель `backend-reviewer`: **opus**, **sonnet** или **нет** для эпика только с документацией. Если строки нет — opus.

## Статусы

- Статус эпика хранится только в этом файле, статус задачи — только в таблице `README.md` её эпика. Файл задачи статуса не хранит.
- Эпик: не начат → в работе → на ревью → готов.
- Задача: не начата → в работе → на доработке → готова.
- Задача «на разработчике» остановилась на решении человека. Причины: исполнитель «разработчик», нужно новое публичное имя, не справился opus, ошибка git без безопасного решения. Задачи, которые от неё зависят, ждут, остальные идут дальше.
- Задача может быть «отклонена» — это решение разработчика, что её не делаем. `/epic` такую задачу не берёт и не ждёт. Задачи, которые от неё зависят, не берутся без нового решения разработчика. Пример: EPIC-2 TASK-4 отклонена 2026-10-27 вместе с таймаутом `SOWA_SHUTDOWN_TIMEOUT_MS`, разработчик решил, что страховка не несёт пользы.
- Статусы обновляет менеджер (основная сессия) по ходу эпика. Статус «готов» эпику ставит разработчик, когда сливает его в `master`. Если разработчик прямо говорит слить в `master`, менеджер сам ставит эпику статус «готов» после слияния.
